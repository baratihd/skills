# Django Product Documentation — Agent Skill

## Mission
Produce a **separate, versionable documentation project** for a Django codebase, or a scoped app/feature. Apply the mandatory **per-section language policy** below; retain literal identifiers (paths, classes, HTTP methods, API fields) in English. Make explanations precise, complete, example-rich, executable as test specifications (not autogenerated test code), and traceable to evidence. Never conflate product/business explanation with technical implementation.

## Inputs and triggers
- Inputs: source repository root, documentation output directory (default `documentation/` relative to repository), scope (`all`, `app:<app_label>`, `feature:<description>`), and update baseline (`git diff` base branch/commit when available).
- Do not demand all inputs upfront. Discover the repository root, existing docs, Git state, Django configuration and relevant modules. Ask for the missing critical input only when it blocks accurate work.
- Ask for **the frontend repository path or frontend documentation directory** only if confirming UI flows, frontend validations, user journeys or E2E integration requires it. Never invent frontend behavior while waiting; document backend-known behavior and mark frontend-dependent claims unresolved. Do not search arbitrary directories outside authorized workspace.
- Never silently broaden a feature-scoped request to the entire repository.

## Non-negotiable rules
1. **No invention.** No inferred business intention is stated as fact solely because of a method name, serializer label, or comment. Record verified code observations separately from unconfirmed business interpretation. Where uncertainty remains, add the **language-specific uncertainty sentence** defined in rule 4 directly after the affected explanation, followed by a concrete unresolved question and missing evidence. Do not use this sentence as a substitute for explaining ambiguity.
2. **Traceability.** Assign stable identifiers: `FEAT-xxx`, `BR-xxx`, `API-xxx`, `FLOW-xxx`, `TEST-xxx`, `GAP-xxx`. Associate each verifiable claim/rule with repository-relative source path + symbol, endpoint, model, existing test, or authoritative document. Add commit SHA and analysis date to metadata. Never fabricate line numbers; use line ranges only when obtained from the actual snapshot.
3. **Separation.** `product/` tells user outcomes, features, roles, user journeys and acceptance criteria; `business/` defines policies, calculations, priority, constraints and exceptions; `technical/` records implementations and contracts; `quality/` contains detailed test specifications; `operations/` contains deployments and runbooks. Cross-link rather than copy technical details into product pages.
4. **Mandatory language and text-direction policy.** Document languages are determined by destination, not by the language of the request, source code, or existing content:
   - `docs/product/**` and `docs/business/**`: **Persian (fa), RTL**.
   - `docs/technical/**` and `docs/quality/**`: **English (en), LTR**, including headings, descriptions, tables, Given/When/Then, sample explanations, acceptance conditions, warnings, labels, unanswered questions and test data descriptions. Do NOT translate code identifiers, payload fields or API values. Do not add Persian narrative or the Persian uncertainty sentence to these two categories.
   - `docs/operations/**`, `docs/index.md`, `docs/glossary.md`, `docs/traceability.md`, `docs/coverage.md`, and `docs/changes.md`: **Persian (fa), RTL** by default; preserve English paths, IDs and code literals.
   - `SKILL.md`, agent-oriented reference instructions, and root README may be English. **Actual published documentation** obeys the section policy regardless of these instruction files.
   - In English sections, when a claim is uncertain, use exactly: **"This section is documented based on the details available in the source code."** followed by a concrete **Needs confirmation** question and missing evidence. In Persian sections use exactly: **«مستند این بخش بر مبنای جزئیات موجود در کد نوشته شده است.»** followed by **نیازمند تأیید**.
   - Site-level RTL must NOT force English page text into RTL. Apply page-scoped `lang`/`dir` via `site/hooks.py` and CSS, while fenced code blocks and literal payloads remain LTR everywhere. Preserve valid Markdown syntax and validate both English and Persian rendered pages.
5. **Testability.** For each relevant behavior document preconditions, inputs, output, state transition, validation, authn/authz, negative cases, boundaries, side effects and expected result. Include Given/When/Then scenarios in **Unit**, **Integration**, **E2E**, and **FireTest** (= smoke/sanity checks in running environment). Provide synthetic example data; **do not generate executable tests** unless separately requested. Clearly flag unsafe production FireTests and describe read-only / isolated substitutes.
6. **Privacy.** Do not print credentials, tokens, customer data, actual PII, private endpoints, secrets from `.env` or environment variables; use masked placeholders. Never execute destructive database actions or real external calls merely to validate docs. Respect access controls and skip inaccessible sources.
7. **Evidence and confidence.** Classify important claims as `Verified by code`, `Verified by test`, `Verified by document`, or `Needs confirmation` in English sections; use `تأییدشده از کد`, `تأییدشده از تست`, `تأییدشده از سند`, or `نیازمند تأیید` in Persian sections. Tests show asserted behavior, not necessarily production guarantees. Mark code-vs-document conflicts explicitly; never conceal them.
8. **Incremental and non-destructive.** Update only when invoked. Use `git diff` (if a baseline is available) to detect affected symbols, APIs, migrations, tasks, settings, tests, and linked documents. Do not erase manually written pages or unsupported content. Summarize pending changes before overwriting ambiguous material. For absent Git baseline, record that impact analysis is limited.
9. **Publishable and portable.** Deliver a stand-alone `mkdocs.yml`, Markdown tree, styling and build/run instructions in output folder; avoid imports or absolute paths to Django repo. Link source using path references and optional configurable source URL, never symlinks needed for publication. Documentation build must not require running Django.
10. **Progress and limits.** For repository-wide documentation, build an inventory first and work in bounded modules; record unreviewed modules as coverage gaps, not as documented. Never claim 100% coverage without comprehensive evidence. State what was inspected, changed, unverified, and build/check results.

## Workflow (follow in this order)
### 1. Discover and bound
- Check `git status`, `git rev-parse HEAD`, repository layout, installed apps/settings, Django/DRF routes and routers, schemas if checked in, models/migrations, serializers/forms, views, services/repositories, permissions, signals, async tasks, integrations, configuration and deployment references, existing tests and docs.
- Use safe static inspection first. Do not run imports or `manage.py` commands if they may perform I/O or alter state. Ask permission before accessing external services.
- Declare selected scope, evidence set, missing modules and Git baseline.

### 2. Build traceable inventories
- Feature inventory: capabilities, actors, entry points, workflows, domain terminology.
- Business inventory: rules, decision tables, priorities, calculations, permissions, exceptions, edge conditions and conflicts.
- Technical inventory: models/fields/constraints, API request/response/status/error formats, authn/authz, transactions/locks, caches, Celery retries/idempotency, signals, scheduled jobs, external dependencies, observability and deployment requirements.
- Distinguish observable behavior from intended behavior. See `references/evidence-and-traceability.md`.

### 3. Resolve ambiguity and frontend dependency
- List pointed questions about missing business policies, conflicting implementations and validation paths. Ask the user when answers materially affect semantics; continue documenting **independently verifiable** sections if unanswered.
- If frontend evidence is necessary, ask specifically: `برای تأیید جریان کاربری و سناریوهای E2E، مسیر پروژه فرانت‌اند یا دایرکتوری مستندات آن چیست؟` Mark frontend-only details `نیازمند تأیید` until inspected.

### 4. Author pages
- Read `references/design-system.md` and retain the Material scaffold under `site/`: three native appearance modes (System default), local assets, page-scoped direction, accessible semantic components and responsive navigation. Do not silently replace it with a generic theme or add font/CDN requests. Use the project Makefile for development.
- Keep the scaffold’s independent Persian/English reader font settings, local script, early initialization and saved allowlisted IDs when generating or updating a site. Configure options through `extra.documentation_fonts`; keep font availability/fallback limits explicit and code fonts independent. See `references/design-system.md`.
- Maintain an editable glossary covering every discovered app/domain and shared concepts. Separate literal code identifiers from product labels, meaning/boundaries, evidence, and approval status. User-approved terminology takes priority over guesses from class names: in Treatment, `AcceptanceRequest` means «درخواست تأیید», currently medication approval only, not document reception. Keep project-specific decisions in the project's glossary/evidence, not universal assumptions. Never rename technical identifiers or propagate unreviewed translations globally; if the user requests glossary review first, wait for their subsequent request before changing other narrative pages.
- Include a root documentation README with the actual tree, quick commands, file ownership/edit map, evidence/registry maintenance, language and metadata rules, glossary review flow, checks and limits. Do not introduce a parallel glossary source of truth.
- Use `references/page-contracts.md` and templates in `templates/`.
- Provide realistic, sanitized examples for at least one successful path and the meaningful error and boundary paths. Specify where behavior is unspecified rather than filling gaps.
- Document diagrams (Mermaid if supported and checked), flow/state transitions and third-party interactions only where evidence supports nodes and transitions.
- Product, business, technical, quality and operations pages must be distinct but cross-linked via stable IDs. Before finalizing, scan all files under `docs/technical/` and `docs/quality/` for Persian narrative, and verify language/direction on generated website pages.

### 5. Generate test specifications
- For every documented feature or business rule, write a scenario matrix with IDs, type, level, dependencies, preconditions, inputs, Given/When/Then, Expected Result, negative/boundary checks, relevant evidence and test-data fixtures (synthetic).
- Unit: local rule/validation pure behavior; Integration: DB, cache, Celery, third parties using controlled doubles; E2E: verified user-to-service path; FireTest: safe smoke/sanity checks against a deployed environment including auth, health, critical happy path, no destructive writes without explicit approval.
- Distinguish **existing tests** from **proposed scenarios**. Do not claim tests ran.

### 6. Change impact and incremental maintenance
- Check Git diff (`merge-base` when suitable; otherwise explicit baseline), including renames and deleted files. Map symbols to trace IDs and pages.
- Inspect impacts on API compatibility, schema/migrations, business rules, user flows, integration contracts and test scenarios; revise dependent pages and stale citations. Add `changes.md` / impact report.
- If no base reference or ambiguous unrelated working-tree changes, do not pretend comparison is exhaustive; ask for baseline or mark report partial.

### 7. Validate and report
- For theme work, run available offline browser checks; verify native System/Light/Dark, live OS changes, manual overrides, reload/navigation persistence, first paint, keyboard/focus, search, code copy, fonts, contrast, desktop/tablet/mobile and both page directions. Capture AND inspect representative light/dark Persian/English screenshots when local browser tools exist. State unsupported assets/diagrams and audit limits explicitly; do not claim full WCAG compliance from token contrast alone. See `references/design-system.md` for scaffold test inputs and missing-font/Mermaid constraints.
- Validate relative links, expected nav pages, ID uniqueness, Markdown fences, mixed-language RTL/LTR layout, Mermaid rendering, source references, response examples against actual serializer/schema/tests when possible, and missing compulsory sections.
- Run `python -m mkdocs build --strict` **only if dependencies are already available or user authorizes setup**; report command, exit status, warnings. Never report successful build without execution.
- Publish `coverage.md` with reviewed/unreviewed counts **and denominator definition**, evidence availability, gaps (`GAP-*`), unresolved business questions, test-case counts by type and confidence; do not use false numeric precision.
- Final agent reply: what was created/updated, scope, traceability/coverage, uncertainty, validation results, missing frontend evidence, and safe next actions.

## Output structure
Use the scaffold under `site/` as a starting point; copy into a directory containing independent `mkdocs.yml` and `docs/`. Expected pages:
- `docs/index.md`, `docs/product/`, `docs/business/`, `docs/technical/`, `docs/quality/`, `docs/operations/`
- `docs/traceability.md`, `docs/coverage.md`, `docs/changes.md`, `docs/glossary.md`
- `.github/workflows/docs.yml` optional, **not enabled by default** because builds/updates only run when explicitly invoked; CI publishing requires approval.

## Acceptance gates
Documentation is not considered complete if: a substantive business rule lacks provenance/status, product and technical content are mixed, an applicable behavior lacks testable expected outcomes, examples contradict evidence, frontend assumptions are silently introduced, identified gaps are hidden, the website is not portable, technical/quality narrative is not English, product/business narrative is not Persian, or build success is asserted without validation. A scope may be delivered as **partial** with precise gaps.
